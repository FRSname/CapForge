# CapForge v3 — the pre-publish hub

**Status:** PROPOSAL with decisions, 2026-09-11. The nine product questions are answered in §11; the milestone table in §7 is the plan to execute, starting with Week 0. Written by the orchestrator from a 13-agent research / design / judge workflow (4 research reports, 6 independent proposals, 3 judging lenses), then adversarially verified by three more agents (codebase, platform sources, internal consistency) whose corrections are folded in. Every codebase claim was re-derived from source before it was kept. Filip's decisions are recorded in §11; everything else is a recommendation.

---

## 0. The short answer

The idea is right, and it is the natural next step for this codebase rather than a pivot. Nobody in the September-2026 landscape combines all four of: a **local word-level transcript** as the source of truth, a **persistent per-video record** on the user's disk, an **agent that reads and writes that record over MCP**, and **no credits or minutes**. Descript and Riverside come closest, but both are cloud-hosted and metered (Descript bills media minutes and AI credits; Riverside gates its MCP to paid Grow+ plans), and their MCPs can only ingest a local file by uploading it — they cannot read or write a record on the user's disk. vidIQ's MCP is read-only analytics. The YouTube MCPs that write (`anwerj/youtube-uploader-mcp`, `pauling-ai/youtube-mcp-server`, `mrchevyceleb/youtube-mcp`) upload or update metadata but hold no transcript and no per-video record; `i1s-abhishek/youtube-studio-mcp` updates metadata and thumbnails only. Kinocut is local and agent-native with a content-addressed project store and a semantic index, but has no browsable library, no durable publish dossier, and publishing is out of scope by design. That intersection is the lane, and CapForge already owns the hard part of it (transcript + three-renderer captions + a working control layer).

Three things reshape the vision before it becomes a plan:

1. **"Connect the channel and upload" is a compliance project, not a button.** Every `videos.insert` from a Google Cloud project that has not passed YouTube's API Compliance Audit is **locked private with no appeal** (projects created after 2020-07-28). Google publishes no turnaround for the audit; developers report multi-week waits and unanswered requests. So the publish path must be designed *zero-risk first*: CapForge produces a copy-ready package and the corrected caption files, and the only API write worth owning later is *updating an already-uploaded video* (metadata, thumbnail, caption tracks) — which is the 95% case for conference recordings anyway. Uploading the file itself stays out until an audited project exists.
2. **The record must be readable when no video is open.** Your flow ("what did I publish in September", batch over thirty conference sessions, a skill writing into CapForge from another Claude session) breaks the current single-session model. That is the one place where "renderer owns, backend mirrors" has to bend: the *dossier* becomes backend-owned durable data; the *session* (transcript, groups, style, tracks) stays renderer-owned exactly as today. Note "no window open" is not "app closed": the backend lives exactly as long as the Electron app (§2.1).
3. **Text generation is the agent's job; CapForge's job is timing, structure, validation, storage and review.** Chapters snapped to real word starts, quotes with exact timestamps, Shorts candidates as timestamps, the corrected transcript as the *published* caption track, per-language metadata riding the translated tracks, deterministic YouTube-limit validators, a channel brief the agent reads once — those only exist because CapForge holds the words. Description prose, titles and keywords come from the LLM through your own skills, which should write *into* CapForge instead of pasting SRT into chat and saving `.txt` files.

The rest of this document is the shape of that product, a performance plan with measured numbers, an honest platform matrix, a cut line for v3.0 that fits a quarter, and the open questions.

## 1. What is true today (verified against source)

- **Single-session app.** `Screen = 'file' | 'progress' | 'results'`; the home screen is one dashed drop zone. There is **no library, no recent list, no per-video metadata**. `app-state.json` is a small UI-prefs store (window bounds, last dialog paths, last preset, favourite fonts, chosen Whisper model); its only video-related keys are `lastProjectPath` / `lastInputPath`, both dialog defaults.
- **Persistence surfaces:** `app-state.json`, `autosave.json` (a single crash-recovery file, tmp+rename, deleted on Save/New, written only on the results screen, with a recovery banner whenever it exists at launch), `presets.json` (written non-atomically), `userData/fonts/`, user-chosen `.capforge` files (v2, additive). The only per-video keyed storage is the HyperFrames workspace at `~/.capforge/studio/<sha1(abs path)[:8]>/` — explicitly intermediate state; it records its source path only in the co-author marker, which is written when co-author mode is entered or left.
- **Backend is a stateless singleton:** `current_result` in memory, one job at a time (`409` while busy), the transcribe POST held open until done, `/api/cancel` signals transcriber and renders together. `require_local_token` already accepts the agent token, so one route set can serve both `api.ts` and `mcp_server/client.py`. The backend is spawned by Electron and stopped on quit: on Windows closing the last window quits the app; on macOS the app stays in the Dock.
- **The agent bridge:** discovery file `~/.capforge/backend.json` (hardcoded; `CAPFORGE_HOME` is honoured by the studio workspace and `workspace_fs` but not by discovery), agent token persisted, 38 MCP tools (34 in `server.py` + 4 from `tracks.py`) all scoped to the *open* session. Tool groups register via `TOOLS + register(mcp, get_client)`; `server.py` is at its size ceiling. The mirror (`PUT /api/ui-state`) is a cache that 404s until the renderer pushes; `load_video` and the three track commands `409` when no window is connected, while the style commands are broadcast regardless and simply vanish. `find_moments` / `find_semantic_moments` (numbers, cta, speaker_change) already exist and are the seed of chapter intelligence. `word_id` there is `f"{si}-{wi}"` — a **positional pair that shifts on delete/merge**; `WordSegment` has no `wid`. Chapters must therefore be stored as **seconds** (timing never shifts), never as `si-wi`.
- **Agent transcript edits are already undoable as a whole:** `AgentLiveSync.applyResult` pushes onto the editor's segment/group undo stack (`useUndoRedo`), so Cmd+Z reverses the last agent edit — but only while the **source** tab is active (with a translated tab open the edit is reconciled straight into the stored track with no undo entry), only as the most recent editor step, and with no per-tool-call granularity or visible attribution.
- **The workspace sandbox already permits `.txt`/`.md` writes** and `_coauthor_root` gates only on `current_result` — which is why the day-zero experiment in §7 costs zero code.
- **Renderer CSP is `img-src 'self' data: blob:`** — any library poster served from `127.0.0.1` must be fetched and turned into a blob/data URL (every library proposal missed this).
- **The macOS Python runtime CapForge installs (3.11.15) has SQLite 3.50.4 with FTS5** — verified on the repo's `resources/python-mac-extracted` and on the installed runtime under Application Support. Windows embeddable Python is unverified. No Node native modules, no DB dependency, `asarUnpack` covers only `backend/**` and `mcp_server/**`.
- **Perf facts:** the window is not created until the backend answers a health poll that starts after a fixed 1 s delay (500 ms steps); the port/token IPC handlers return a snapshot (the `53421` fallback / empty token) if called before startup finishes; the Whisper model is loaded on the first transcription after launch and then retained across jobs of the same size (nothing warms it earlier); `transcribe()` loads the alignment model through the *uncached* path and `del`s it in `finally` while the per-language cache (`_load_align_model`) is used only by realign; the installed whisperx 3.8.6 defaults `load_model` to `threads=4`; encoders are `libx264 -preset medium`, `libvpx-vp9`, `prores_ks` (no hardware paths); WaveSurfer is created with `media: videoEl` and **no `peaks`**, so it downloads and WebAudio-decodes the whole media file before Play enables; there is **no `React.memo` anywhere** and playback ticks (16 ms) re-render the entire editor tree; the mirror rebuilds the full render body and autosave stringifies the whole project synchronously on every slider tick (only the PUT/write is debounced).
- **Files already past the 800-line ceiling:** `main.py` 1869, `video_render.py` 1819, `useSubtitleOverlay.ts` 968, `server.py` 921, `useTimeline.ts` 840, `App.tsx` 777, `ResultsScreen.tsx` 748. `App.tsx` and `AgentLiveSync.tsx` (372) are the landing zone of every deliverable below, so §7 starts with extractions and the PR gate is "neither file grows".
- **Your existing skills** (`transcript-breakdown`, `update-yt-description`, installed under Claude Desktop's skills-plugin directory) already define the output: title options, ~2000-char description, WHAT YOU'LL LEARN, QUOTE, CHAPTERS, LINKS, SPEAKER, keywords line, hashtags, SHORT DESCRIPTION, Shorts caption + clip suggestions, and six "before you finish" checks the model does badly (character counting, dash hunting). Those checks and that shape are the record's field list.

## 2. The bet: the video record

One durable object per video, and the agent's contract is built on it.

### 2.1 Ownership rule (the one new rule)

> **Session state stays renderer-owned; the dossier is backend-owned.** The renderer keeps owning transcript, groups, style, tracks and *which video is open* (opening a record is still a command, `409` without a window, confirmed by mirror echo). The backend owns `record.json` (the dossier), the derived transcript snapshot, the poster and thumbnails, and a disposable search index. The MCP agent reads and writes the dossier over the token-gated HTTP boundary with **no window required**; it needs `open_video` only for live transcript/style edits.

Why bend the rule here: the mirror is a cache that 404s until the renderer pushes and the commands that matter `409` with no window; confirm-by-poll exists *because* writes route through the renderer. A library must be readable on the drop screen and writable by two clients, so it is document data, not session state. The backend already persists the co-author marker and scaffold fingerprint per video; `PUT /api/agent/result → broadcast → renderer re-fetches` is the existing "agent writes durable state, renderer follows" seam, made persistent.

**Lifetime.** The library is served by the app's backend, so **CapForge must be running** (the window may be closed on macOS; on Windows closing the window quits). Library tools raise `BackendNotFound('CapForge is not running — launch it (the window can stay closed) and retry')`; `open_video` raises `409 'CapForge is running but no window is open — click the Dock icon'`. There is deliberately no headless backend and no launch-on-demand daemon: when CapForge is quit, it is quit, and nothing of it keeps running (decision D9).

**Single writer.** The library is single-writer per backend and `backend.json` is the only discovery record, so a second CapForge instance would hijack the agent: add `app.requestSingleInstanceLock()` (second launch forwards its dropped path to the first). Multi-window is out of scope for v3.0.

### 2.2 Layout on disk

```
~/.capforge/library/                 (CAPFORGE_HOME honoured everywhere, discovery included — today it is not)
  brief.json                         channel brief: voice, audience, never-say, templates
  collections/<id>.json              per-collection overrides + templates (v3.0 stretch)
  library.db                         SQLite (WAL) index — DISPOSABLE, rebuilt from folders
  .scratch/<id>/                     scratch records (`scratch: true`), hidden from the library, pruned at lifespan after N days
  <video_id>/
    record.json                      the dossier (authored + system fields, rev, history)
    project.capforge                 the session snapshot, renderer-composed, v2 format (PUT by the renderer)
    transcript.json                  DERIVED by the backend from that PUT, same atomic write, same rev
    peaks.bin                        waveform peaks (perf §5) — cache, keyed size+mtime
    poster.jpg                       poster (import), replaceable from the player
    thumbnails/<hex>.jpg             frame grabs the user or agent took (capped)
```

Human-readable files are the truth; the DB is a cache with `rebuild_index()` at lifespan when missing or `schema_version` differs, and a `LIKE` fallback if FTS5 is absent (Windows). Every write is tmp + `os.replace` (the precedent in `hyperframes_project.py` / `agent_bridge.py`); `presets.json`'s non-atomic write is the anti-pattern. **One write rule for the transcript:** the renderer PUTs `project.capforge`; the backend derives `transcript.json` in the same write; `autosave.json` is written only when that PUT fails (§7 #3, §9.1). Assets are served by `GET /api/library/{id}/asset/{name}` with a **fixed name allowlist** (`poster.jpg`, `peaks.bin`, `thumbnails/<hex>.jpg`) resolved strictly under the record folder — never a client-supplied path; `_is_servable_path` stays untouched. A queue-produced record (§5) may hold `transcript.json` with **no** `project.capforge` (status `transcribed`); opening it composes the session from the bare transcript (`ensureWordIds`, default settings, auto groups) and the renderer then writes the first `project.capforge` — the only path where the backend authors a transcript.

**Disk:** a 60-minute talk is ~3 MB of JSON per copy; with peaks (~0.5 MB), a poster and a thumbnail cap the footprint is well under 10 MB per record. `history[]` is capped with `prev` truncated for long text; scratch records are pruned. `~/.capforge` is outside `userData`, so app uninstallers will not remove it — the Settings library-path row says so, with Reveal, and "Export record… / Import record…" (a zip of the folder) is the user-facing backup path (v3.x).

### 2.3 Identity, revisions, status

- **`video_id`** is a UUID minted at record creation (a fingerprint changes on re-encode, a path hash on move — neither is a stable id). `load_video`, `transcribe`, `open_video` and `get_status` return or carry it, the mirror's `activeVideoId` is the same value, and `get_video` also accepts `path` for one-shot lookups.
- **Identity:** content fingerprint (size + mtime + sha1 of first/last 1 MB) plus `sourceTag = sha1(abs path)[:8]` as a *join key* to the existing studio workspace. Moving a conference folder after the event must not orphan thirty records → "Locate…" relinks by fingerprint, rewrites `sourceTag`, and renames the studio folder old→new (or keeps a `sourceTags[]` history the workspace lookup tries in order) so the scaffold cache, co-author marker and Week-0 `notes/` follow the file. The record contract test covers a relinked record.
- **Revisions:** `PATCH /api/library/{id}` requires `If-Match: rev`; a stale write gets `409` **with the current record in the body** so the agent re-reads instead of clobbering (new — today's 409s, e.g. `sync_captions`, carry only a detail string). Every write stamps `{field, prev, by: 'agent'|'user', at}` into a capped history from day one — cheap to stamp, expensive to retrofit. The "changed by agent" chip + Revert ship before any diff UI.
- **Status** (`imported → transcribed → captioned → drafted → published`) is **derived at read time**, never stored: segments>0, `renders[]` non-empty, description non-empty, `publish.youtube.videoId` set. `renders[]` is appended via an optional `record_id` on the **request** models (`VideoRenderRequest`, `HyperframesRenderRequest`, `ExportRequest`) — never on `VideoRenderConfig`, so `test_caption_cfg_contract.py` stays green. A derived **"captions newer than published"** flag (transcript `updatedAt` > `publishedAt`) keeps the status rail honest. "Captioned" means a render exists (decision D8).
- **Creation:** on drop/import or by the agent's `load_video` / `transcribe` — never silently at every transcript-write site. Both agent tools take `scratch` (default `false`, because the batch path is real videos); with `scratch: true` a **scratch record** is still created — so `video_id` exists for every session — but under `.scratch/<id>/` with the `scratch` system field set: it is excluded from `list_videos` unless `include_scratch`, its dossier is read-only (`set_video_meta` refuses with a clear error; the mirror carries `scratch: true`), it is pruned after N days, and "Keep" / `set_video_meta(id, {scratch: false})` promotes it into the library. If a real record already exists for the fingerprint, a scratch open uses it for session state without autosaving into it. This keeps agent QA runs and test clips out of the library.
- **Removal:** "Remove from library" (keeps every file) and "Delete record" (record folder to Trash via `shell.trashItem`; never the source media; `renders[]` outputs and the studio workspace asked about separately). No agent delete tool in v3.0.
- **`.capforge` files:** `project.capforge` inside the record is the primary session document. The dialog-based save survives as **"Export project file…"** and writes the v2 *session* snapshot — it backs up the session, not the dossier (a v2 file cannot carry `record.json`; the record folder / the v3.x sidecar is the dossier's backup). `migrateProjectFile` stays the only trust boundary. Opening a record via the card and via the agent's `open_video` must produce identical track stores — which is why the pure part of `restoreFromProjectFile` is extracted into `lib/projectRestore.ts` first (§7), so the test is a plain node test. On open, compare `rev`/mtime and prompt when an exported file and the record diverge.
- **Contract test:** a partition test in the spirit of `test_caption_cfg_contract.py` — every `VideoRecord` field filed as authored / backend-derived / session-owned / mirrored-to-MCP — so a new dossier field can't silently drop out of the mirror, the MCP shape, or the export.

### 2.4 The dossier

**Authored fields** (from your skills): `title_options[]`, `title`, `description`, `short_description`, `chapters[{start_s, title}]` (seconds; snapped to a word start for display; `unanchored` flag if the word is gone), `tags[]`, `hashtags[]`, `keywords[]`, `summary_md`, `highlights[{text, start_s, end_s}]`, `quotes[{text, start_s, end_s, speaker}]`, `tools_mentioned[]`, `links[{label, url}]`, `shorts{caption, clip_suggestions[{start_s, end_s, why}]}`, `thumbnail{ideas[{label, type, headline, subtext?, visual_suggestion?, recommended}], candidates[], cover}`, `speakers{SPEAKER_00: {name, handle, url}}`, `collection_id`, `localized{lang: {…}}`, `publish{youtube{videoId, url, publishedAt}, pushes[]}`, `external_refs[{system, id, url}]`. The un-namespaced fields are in the brief's `language`; `localized[lang]` carries the full authored set for that language (title, description, short_description, tags, hashtags, chapter titles, shorts caption), and `get_upload_package` / `validate_video` take `lang?` (the 5000-byte limit differs per script). Per-track SRT/VTT export pairs with `localized[lang]` by track language.

**System fields** (so the contract test has a complete list on day one): `id`, `rev`, `fingerprint`, `sourceTag`, `sourcePath`, `duration`, `language`, `renders[]`, `history[]`, `createdAt`, `updatedAt`, `publishedAt`, `scratch`, `missing_media`.

Two additions no proposal had and the judges called out:

- **Named speakers.** Diarization yields `SPEAKER_00/01`; nothing lets a human or agent name them. A per-video (or per-collection) speaker map feeds the description's SPEAKER block, chapter candidates, quote attribution and future caption labels. Your breakdown skill's "resolve speakers" step becomes a lookup.
- **Collections / events.** A conference is forty videos sharing 90% of the boilerplate (recorded-at line, hashtags, speaker block format, playlist, feedback URL). Records belong to a collection with **collection-level brief overrides** and template slots (`{{title}} {{speaker}} {{event}} {{chapters}} {{links}}`), so the agent writes only the per-video paragraph and a whole event's descriptions can be regenerated when a sponsor line changes. Overrides live on the collection, not the video; if a per-video escape hatch is ever wanted it is one named field (`feedback_url`), with a reason.

## 3. What the agent gets

### 3.1 Library tool group (`mcp_server/library.py`, same shape as `tracks.py`)

`list_videos(status?, collection?, q?)` · `get_video(id | path)` (dossier without transcript) · `get_video_transcript(id, segments_only=True)` (from `transcript.json`; works with no window; for the *active* record it proxies to the live result, and every response carries `{rev, source: 'record' | 'session'}` so the agent knows which it read) · `set_video_meta(id, patch, rev)` (merge; carries `chapters` like any authored field; `409` returns current; `422 {violations}` on hard-limit failures) · `check_chapters(id, chapters)` (pure: returns `{violations[]}`; snapping to a word start stays in the renderer, for display) · `find_video_moments(id, query | kind)` (library-scoped variant of the moments detectors over the stored transcript) · `search_library(q)` (FTS) · `grab_frames(id, times[])` · `get_brief()` / `set_brief(patch)` · `get_upload_package(id, platform, lang?)` · `validate_video(id, lang?)` · `mark_published(id, {videoId, url, publishedAt})` (tier 1 — recording a URL the user pasted is not outward-facing) · `open_video(id)` — the **one** tool that stays a renderer command (new `AGENT_COMMAND_OPS` entry in `backend/main.py`, `409` without a window, confirmed via the `activeVideoId` mirror key, restored through the same `lib/projectRestore.ts` path as the card). Everything in this list is deliverable #2 (core) except `grab_frames` and the `lang?` parameters, which arrive with the 4s stretch editors. `open_video` first flushes the pending record autosave, refuses with `409 unsaved_scratch_session` when the current session is scratch and dirty, and is refused while `screen === 'progress'`; the card click follows the same rule with a confirm dialog.

Transcript *edits* stay session-only on purpose: `wid`, `retimeWords` and `reconcileGroups` live in the renderer, so `update_words` keeps requiring `open_video` first — say so in the docstrings or agents will try `set_video_meta` for text fixes.

Two S-effort inputs every chapter path needs, worth shipping first: `duration` in `get_transcript`'s `segments_only` shape (the full shape already carries it), and a **`pause`** kind in `find_semantic_moments` (segment gap ≥ `PAUSE_MIN_S`).

### 3.2 Channel brief (structured, small)

`brief.json`: voice, audience, `language`, never-say list, and templates (title suffix, description footer, recorded-at line, speaker block, feedback URL, default hashtags, link rows, description length window, short-description limit). Edited in a Settings card beside "Claude AI integration"; exposed as `get_brief` and a `capforge://brief` resource so the agent pulls it once per session. It is exactly the conference-specific prose in `update-yt-description` today, moved from skill text into user data — which is what lets one skill serve a personal channel and a conference channel. Keep it structured; prose eats context on every call. Decision D2: a global brief plus per-collection overrides, kept general so any user can shape it to their channel, not just a conference vs personal split.

### 3.3 Validators: one implementation, in Python

All validation lives behind `POST /api/library/validate` (body = the dossier fields, so unsaved panel text validates too): YouTube **hard limits** always (title ≤ 100 chars, description ≤ 5000 bytes, tags ≤ 500 chars total, no `<`/`>`, chapters start at `00:00`, ≥ 3, ascending, ≥ 10 s apart, ≤ duration); **house-style** rules only when the brief asks for them (em/en dash hunt outside numeric ranges, the 1800–2200 window, the 12–20-term keyword line, first-150-characters hook). The Publish panel calls it on its debounce and renders findings under each field; `set_video_meta` refuses hard-limit violations with `422`. `lib/youtubeRules.ts` keeps only what needs the live words or is display-only: chapter **snapping** to a word start, `MM:SS`/`H:MM:SS` formatting, and byte/char meters. No fixture-pinned twin of the rules.

### 3.4 Shipped workflow knowledge

Reuse `knowledge.py`'s manifest/allowlist pattern for a `publish` topic set (workflow, breakdown, description, chapters, thumbnails, shorts, batch), a `publish_guide(topic?)` tool, `capforge://publish/{topic}` resources, and `@mcp.prompt()` prompts Claude Desktop lists as slash commands (`breakdown(video_id)`, `describe(video_id)`, `chapters(video_id)`, `batch_publish(status)`) — FastMCP in the dev venv exposes `prompt` and `resource`. A test must assert every tool named in the guide exists on the server, or it drifts. Installing a `SKILL.md` into `~/.claude/skills` from "Connect Code" must be opt-in with a visible path.

**Port of your two skills** (the first customers — if they are not retargeted, the record stays empty and the demo has no data; this is why the port sits in deliverable #4, not #5): `transcript-breakdown` Part 1 writes `summary_md`, `highlights` (now with real timestamps from `find_video_moments`), `quotes`, `tools_mentioned`; its Parts 2–3 (resolve the event and speakers, then `set_update_talk`) become an optional second destination the agent chains to, mapped from the record (`summary_md → summaryMd`, `title`, `speakers → speakerIds` via the existing resolve step, `publish.youtube.url → videoUrl`). `update-yt-description` reads `get_video` + `get_brief`, writes structured fields (chapters and title options as **data**, not `MM:SS` lines in prose), runs `validate_video`, and its Saving step becomes `get_upload_package` + its optional Update-conf store step, `set_session_enrichment`. Both pushes are a **mapping, not a copy** — `set_session_enrichment` takes `longDescriptionMd`, `youtubeDescription` (≤ 5000), `youtubeShortDescription` (≤ 200), `highlights: string[]`, `customLinks[{label,url}]`, `youtubeThumbnailHooks[…]` (≤ 5), `coverImageUrl`, `slidesUrl`, `videoUrl` — so the dossier is shaped to make them cheap (`links[{label,url}]`, `thumbnail.ideas[]` as the hooks object, `short_description ≤ 200` as a house rule when the brief targets Update-conf, `highlights[].text` at push time), and every push is recorded in `external_refs[{system:'update-conf', id, url}]` and `publish.pushes[]`. Decision D3: Update-conf stays a separate, much larger conference database; CapForge's record is the video-side store and the skills push into Update-conf as a second, mapped destination. To keep one source of truth for the description, the skill writes the record first and pushes from it, never the other way round.

### 3.5 Confirmation model (three tiers, pinned by tests)

1. **Auto-apply with revert:** dossier writes (`set_video_meta`, `mark_published`) apply immediately (a modal per write kills a thirty-video batch), guarded by `rev`, with per-field history and one-click Revert.
2. **Soft lock:** `AgentLiveSync`'s `editingRef` extends to every publish field; an agent write into the field you are typing in queues behind the existing "Agent updated — Apply / Dismiss" banner. Must ship *with* the Publish panel, not after.
3. **Blocking approval:** `_await_render_approval` generalises to `_await_approval(kind, summary)`; anything outward-facing (v3.x platform writes) shows a real summary sheet (title, first 150 chars, chapter count, thumbnail, quota). Approval-tier tools are window-required (`409` without a UI) and get a shorter timeout than `RENDER_APPROVAL_TIMEOUT` (600 s) so a batch loop is not parked on an unattended sheet. No *new* v3.0 tool reaches this tier; `render` / `render_hyperframes` stay its only occupants and the test pins that set.

Rules: no tool mutates more than one video per call (batch is the agent looping, each step visible); a test asserts which tools reach `_await_approval`.

### 3.6 Agent presence (the demo)

A ref-backed `lib/agentTouches.ts` fed by the events `AgentLiveSync` already routes: the slider Claude touched glows brand-orange for a second (`data-agent-touched` on `StudioRow`), words changed by `result_updated` get a fading orange underline (diff `{wid,text}` pairs the way `trackStaleness` does), a new track tab pulses, and an **Activity rail** lists each tool call (`update_words · 3 words in segment 12`) with click-to-jump. It doubles as the review surface for auto-applied writes and — with `lcsPairs` exported from `wordTiming.ts` (module-private today) — gives a *targeted* "Revert Claude's last transcript edit" with attribution, where today Cmd+Z can only pop the most recent editor step.

## 4. What you see (visual)

The current language is a dense "pro dark studio": 13 px Inter, 10 px mono uppercase labels, Instrument Serif italic display, five surface steps, hairline borders, blue accent + brand orange, `--ease-out-expo` / `--ease-spring` tokens (the spring is used exactly once). Strongest screens: StudioPanel, the player stack, TrackTabs. Weakest: the drop screen, ProgressScreen (a generic Lottie, a bar parked at 15% for minutes, no elapsed/ETA), SettingsPanel, PresetPicker's "Abc" chip. **Screens and surfaces:**

| Where you wait | Today | Change | Expected |
|---|---|---|---|
| Startup | window created only after backend health poll (1 s floor + 500 ms steps); backend answers at ~540 ms; port/token IPC returns a snapshot before readiness | `createWindow()` first, spawn backend in parallel, poll at 100 ms, port/token IPC that resolves only once the backend is ready (both preloads — after the preload-parity test lands) | usable window ≤ 600 ms |
| Settings open / every transcribe | `detect_hardware()` imports torch + shells to `sysctl` inside async handlers (~700 ms, blocks the loop) | `lru_cache` + lifespan pre-warm in a thread | ≤ 50 ms |
| First Start after launch | 6.7 s model load on the critical path (retained across later jobs of the same size); alignment model reloaded and `del`'d every job | `POST /api/warm` on file drop under a lock shared with `transcribe()`; use the cached `_load_align_model` inside `transcribe()`; a "free model after job" toggle for low-RAM machines that wires the existing `unload_model()` to run after a job (today it fires only on a model-size switch) | Start → first progress ≤ 0.5 s warm |
| Transcription throughput | `threads=4` default → 3.7× realtime | `threads=os.cpu_count()` in `_load_model` | 4.9× (+32%, one line) |
| Progress during Whisper | single blocking call, bar sits at 15% for minutes | `backend/engine/streaming.py` re-implementing the pinned whisperx 3.8.6 loop over its public pieces, `partial_text` + true % on `ProgressUpdate`, guarded by a symbol-import test | ≥ 1 event/s, words visible ≤ 12 s cold |
| Opening a long 4K talk | WaveSurfer downloads + WebAudio-decodes the whole file; Play disabled meanwhile | `GET /api/library/{id}/asset/peaks.bin` (ffmpeg → 8 kHz mono → Int8 buckets, ~0.06 s/min, cached in the record folder) passed as `peaks`+`duration`; poster via `_grab_source_frame` at import | player interactive ≤ 1 s, RSS delta ≤ 50 MB |
| Playback | ~60 whole-tree React commits/s; overlay + timeline canvases fully redrawn every tick | `lib/playhead.ts` external store + `useSyncExternalStore`, `React.memo` on rows, `lib/frameStateKey.ts` twin of `_frame_state_key` pinned by a shared fixture (a cache key, not a renderer) | ≤ 3 commits/tick, draws ≈ distinct frame states |
| Slider drag | full render body + project `JSON.stringify` per pixel (8 ms on a 9000-word project) | serialize inside the debounce, revision counter instead of string compare, draft value during drag; must still fire within ~300 ms or confirm-by-poll (5 s) starts timing out | ≤ 1 ms/event |
| Baked 1080p render | 104 fps: Pillow 1.8 s/min, Python source-frame round trip 3.5 s, x264 medium 10 s | `encode_preset: draft\|standard\|master` on the **request** models; single-ffmpeg baked compositing via `overlay` (Python writes only cached overlay bytes); capability-probed `prores_videotoolbox` for MOV **only if** the BT.709 + premultiply invariants in `test_overlay_alpha.py` still hold; ETA in the modal | 1 h baked ≈ 17 → 7 min; MOV ≈ 21 → 4 min |
| Ten recordings after a conference day | one job at a time, POST held open, agent batch needs a live session | real **job queue**: `jobs` table in `library.db`, `POST/GET/DELETE /api/jobs`, one sequential worker running backend `transcribe` jobs (not a routed `load_video`, which stays a renderer command), per-job `job_id` on `ProgressUpdate`, results as `transcript.json` in the record folder (§2.2); the v3.x **watch folder** auto-transcribes new files through the queue (the 3s watch folder only imports them) | drop ten talks, go to bed |
| Apple Silicon ASR | CTranslate2 has no MPS backend | 3-day timeboxed `mlx-whisper` spike behind an `AsrEngine` seam, alignment unchanged; go/no-go on rtf ≥ 12× and WER on the Czech + English fixtures | 60-min talk ≈ 16 → ~4 min |

Not doing: `h264_videotoolbox` as default (1.25× on M4; x264 `veryfast` is 1.9×), parallel transcription jobs (CT2 saturates the cores), OffscreenCanvas/workers for the preview, virtualizing rows before memoization, loading the model at startup unconditionally (+2.1 GB idle). CI gets **ratios and counts** (cached-frame cost ≤ 5% of fresh, zero gap-frame bytes in baked mode, `frameStateKey` fixture parity, memo assertions, poll-schedule constants, a gzip ceiling on the renderer chunk); wall-clock numbers live in a local `npm run perf` suite writing `docs/perf/baseline-<host>.json`, with today's numbers as the first baseline and structured `[perf]` log lines per job.

## 6. Publishing: the honest platform matrix

| Platform | What is realistic from a desktop app | Why |
|---|---|---|
| **YouTube — prepare** | Copy-ready package (title, description with chapter block and hashtags, tags line), per-track SRT/VTT, thumbnail JPEG ≤ 2 MB, "Copy plain transcript" for Studio's auto-sync, pinned-comment and community-post drafts, end-screen/card placement suggestions from the CTA detector | zero API risk; this is 100% of the value for anyone who never connects a channel |
| **YouTube — update an existing video** | `videos.update` (50 units; carry `categoryId` from a live read; re-send unchecked fields or they blank), `captions.list` (50) + `captions.insert` per track (400; replace/keep sheet when a same-language track exists), `thumbnails.set` (50) | not subject to the private lock; the corrected transcript replacing auto-captions on thirty videos a year is the one write only CapForge makes valuable. | **YouTube — upload** | `videos.insert` only behind an explicit compliance-audit attestation, resumable, with the warning repeated on the sheet | unaudited → private forever, no appeal; no published audit turnaround, multi-week waits reported, periodic re-audits |

| **Instagram** | clipboard (≤ 2200, ≤ 30 hashtags, "link in bio") | Meta must cURL a **public URL** — a desktop app would need a hosting relay |

**Sequencing for YouTube API work:** v3.0 ships none of it. v3.x-a: chain CapForge's MCP with an external BYO-credentials YouTube MCP (`anwerj/youtube-uploader-mcp` for captions via `force-ssl`, or `i1s-abhishek/youtube-studio-mcp` for metadata) on one real already-uploaded video — hours of work, tells us whether CapForge ever needs to own OAuth. v3.x-b, only if that fails for a reason CapForge can fix: Electron-main OAuth (system browser via `shell.openExternal`, loopback `127.0.0.1:{port}` + PKCE, `youtube.force-ssl` requested once because installed apps get no incremental auth, refresh token under `safeStorage` only — never in `app-state.json`, `.capforge`, autosave, the mirror or the Python env), a pre-flight sheet as the single gate for button and agent, a step-level ledger (retry only failed steps; revert from `remoteBefore`), a quota ledger (10,000 units/day + a 100-uploads/day bucket + 100 searches/day since 2026-06-01). ## 7. Milestones and the cut line

The consistency critic costed the full table below at roughly 16–18 solo weeks before Windows re-test and manual QA — more than a quarter. So v3.0 is split into **core** (≈ 11–12 weeks, the "zero manual fixes" exit test) and **stretch** (ships in the same release only if time allows; otherwise v3.1). The cut order is stated so nothing is dropped by accident.

**Week 0 — de-risking that costs hours, not weeks:**

- **The day-zero experiment (no code).** Sanction a `notes/` folder in the existing co-author workspace (docstring + README recipe) and retarget `update-yt-description`'s Saving step at `write_workspace_file('notes/youtube.txt')`. Publish two or three real videos through it and read the notes back in a later session. This tells us which fields the agent actually reads back before the schema is frozen.
- **Preload-parity test** (assert `electron/preload.js` and `src/preload/index.ts` expose the same `window.subforge.*` names) — lands *before* any IPC change below.
- **Extractions that keep `App.tsx` under the ceiling:** mirror effects → `hooks/useUiStateMirror.ts`; crash recovery → `hooks/useCrashRecovery.ts`; the pure part of `restoreFromProjectFile` → `lib/projectRestore.ts`. PR gate from here on: `App.tsx` and `AgentLiveSync.tsx` do not grow.

The lazy serialization is a *prerequisite*: `tracks[]` plus a dossier riding the mirror every 300 ms would otherwise make slider drags on long transcripts visibly worse.

## 8. Not doing (and why)

- **Uploading video files to YouTube from CapForge in v3.0**, or shipping a CapForge-owned Google client — see §6.
- **API posting to Instagram, X, LinkedIn; TikTok until someone runs its audit.** None of them touch the transcript.
- **In-app "Generate description / titles / keywords" buttons with baked prompts.** The LLM in the chat already does this through your tuned skills; a button forks those prompts into the app and lands CapForge in vidIQ's "generic output" bucket.
- **Keyword extraction / topic segmentation as Python code** (RAKE, TF-IDF, embeddings): worse than the LLM with the transcript in context, and a new model dependency.
- **Thumbnail image generation or scoring, title/thumbnail A/B testing, analytics chat, idea brainstorming.** YouTube Studio (Test & Compare, Ask Studio, auto-dubbing) and vidIQ/1of10/Spotter own these, mostly for free; off-thesis.
- **Trimming, cutting, or Shorts clip export.** Locked decision. Shorts are candidate timestamps the user cuts elsewhere.
- **Anything publish-related in `VideoRenderConfig` or any of the three caption renderers.** `record_id`, `encode_preset`, `output_name_suffix` live on request models.
- **Native Node SQLite (`better-sqlite3`) or `electron-store`.** No native modules today, no rebuild pipeline; Python stdlib `sqlite3` is free. The MCP process never opens the DB — it runs from `app.asar.unpacked` with only `mcp` + `httpx`; the token-gated HTTP boundary is the trust model.
- **Auto-triggered agent work on transcription done.** No "describe this for me" without a prompt.
- **An unpinned second implementation of any rule.** Validation lives in Python once (§3.3); chapter snapping lives in TS once. If a twin is ever unavoidable it is pinned by a shared JSON fixture (the RSVP precedent) or it does not ship.
- **An agent delete tool, multi-window, or a second CapForge instance** in v3.0.
- **New IPC where a backend route or `navigator.clipboard` will do.** Every IPC is a three-file dual-preload edit, guarded by the Week-0 parity test.

## 9. Risks and rules the reviewer must enforce

1. **Two owners of durable state.** Record is primary; exported `.capforge` backs up the session only; `autosave.json` is the backend-down fallback with a toast, never a silent divergence; rev/mtime rule on open.
2. **Chapters are seconds.** Never `si-wi`; a test pins that a `delete` before a chapter leaves its time unchanged.
3. **Size ceilings.** Week-0 extractions first; then new modules only: `backend/library/`, `mcp_server/library.py`, `hooks/usePublishRecord.ts`, `lib/projectRestore.ts`, `lib/youtubeRules.ts`, `lib/publishFormats.ts`, `components/library/`, `components/publish/`. `App.tsx` and `AgentLiveSync.tsx` must not grow.
4. **CSP.** Posters/thumbnails/peaks via the fixed-name asset route and fetch→blob, or widen `img-src` deliberately.
5. **Mirror growth.** Lazy serialization lands *before* `activeVideoId`/`workspace`/publish summary join the mirror; the 300 ms debounce must keep confirm-by-poll (5 s) happy. MCP read-budget policy: dossier and stored transcript from the record routes; only the active track/settings from the mirror; `get_video_transcript` defaults to `segments_only`.
6. **Windows** is unverified on FTS5, `safeStorage`, and loopback. `LIKE` fallback + rebuild-from-folders from day one; a Windows CI check for `_sqlite3` before v3.0 lands; YouTube writes Mac-first.
7. **Agent/user collisions** on the same dossier field must render (chip + reload or soft lock), never swallow the `409`.
8. **Confirmation tiers pinned by tests** — a write tool reaching `_await_approval` by accident stalls a batch; one missing it surprises you.
9. **Token budget.** A 60-minute talk is ~3 MB of JSON; the brief is structured; the mirror is stripped of what the record already serves.
10. **Vitest is the node environment** (render-to-string, no DOM events): diff/revert, chapter snapping, package builders, `projectRestore` and dossier state live in pure `lib/` modules with fixtures, or the largest UI surface ships untested.
11. **Stored-transcript freshness.** While a video is open, `transcript.json` lags live edits by the autosave debounce; the `{rev, source}` envelope (§3.1) is what keeps the agent honest.
12. **Scope.** Summed, the six proposals are years. v3.0 core is the table in §7; anything not in it needs its own plan doc.

## 10. Ideas nobody proposed that belong on the list

- **Glossary / corrections dictionary** per channel or collection (speaker names, product names, "CapForge" not "cap forge", event names) that feeds WhisperX's `initial_prompt` at transcribe time **and** the agent's fix-spelling pass, learned from your manual corrections. Across thirty recordings the same proper nouns are mis-heard the same way — the biggest metadata-quality win nobody costed, and the natural companion to the brief.
- **Timestamp-anchored provenance** for dossier claims: highlights, quotes and description sentences carry `{start, end}` and click-to-seek; `set_video_meta` validates cited times fall inside the media.
- **Batch-apply from the UI** (multi-select: hashtags, footer, tags, playlist, publish state across a collection). The one-video-per-tool rule is right for the agent; the human needs the multi-select.
- **A launch-story counter** on the library screen: hours transcribed locally, renders produced, "nothing left this machine", $0. Free/local/unmetered is a positioning statement against every $15–69/month competitor; make it visible.
